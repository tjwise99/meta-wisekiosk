# RAUC key rotation

This explains how to rotate the RAUC signing key the wisekiosk devices trust, and why the
rotation has to happen in a specific order. It assumes you know what RAUC and a keyring are;
see [`layers-and-kas.md`](layers-and-kas.md) for how the bundle recipe and keyring fit into the
build.

## Why rotate

The device trusts `/etc/rauc/keyring.pem` and verifies every update bundle's signature against
it. Until this rotation, that keyring was upstream's public development certificate,
`development.cert.pem` (CN `AutonomOS Development Key`, SHA-256
`BF:47:F6:ED:4B:FB:8C:86:B5:B2:5A:FC:D9:E8:07:C6:AB:DF:C0:0A:D7:70:07:0C:C6:FB:E3:7E:AE:85:E2:91`).
Its private key, `development.key.pem`, is committed alongside it in the public
`meta-autonomos-core` tree — so anyone with a clone of that repo can sign a bundle this kiosk
will accept as authentic. This is tracked as issue #6 RAUC signing private key is committed in
this public repository.

Rotation replaces the trusted keyring with a per-project key, generated by
`tools/rauc-keygen.sh` into `local/keys/<name>/`. The 2026 key: CN `WiseKiosk Signing Key 2026`,
SHA-256
`E1:85:72:7F:27:19:9E:12:84:7F:55:72:AF:0C:D8:10:CC:8A:64:3A:8E:C4:FD:5C:65:9A:AF:68:D1:59:02:C9`.

`local/` is gitignored, so the key is never committed — but it does sit inside the working tree,
because that tree is what `kas-container` mounts and the build has to be able to read the key to
sign with it. There is exactly one key home; see the prerequisite below.

## Build prerequisite: the signing key must be present

`kiosk-zero-w.yaml` points `AUTONOMOS_RAUC_KEY_DIR` at `local/keys/kiosk-2026`, so **every**
ordinary build signs with that key and bakes its certificate as the device keyring. The key is not
in the repository and cannot be — a fresh clone therefore does not have it, and `just build` halts
during recipe parsing, before any task runs:

    ERROR: .../rauc-conf.bb: Unable to get checksum for rauc-conf SRC_URI entry
    signing.cert.pem: file could not be found

That is the intended behaviour: a missing key stops the build outright rather than quietly falling
back to some other key and producing an image the fleet will not accept.

Before the first build, put the fleet key at
`local/keys/kiosk-2026/{signing.key.pem,signing.cert.pem}`, either by copying the existing pair in
from wherever it is held, or, for a new fleet, by generating one:

    just rotate-keygen kiosk-2026

Copying an existing key in is the normal case: a device only trusts the certificate already baked
into its running slot, so generating a *fresh* key does not give you access to a fielded fleet —
that needs a full rotation, below. `rauc-keygen.sh` refuses to overwrite an existing pair for the
same reason.

A card reflash is the only way to un-rotate a fielded unit — RAUC never rewrites the boot
partition, so no OTA can repair a card written with the wrong keyring. `just flash` therefore
verifies the image's baked `/etc/rauc/keyring.pem` against this key and refuses to write if they
differ, or if the image and rootfs artifacts come from different builds.

## The ordering constraint

A device verifies a bundle's signature against the keyring in the slot it is **currently
running from** — not against whatever the new bundle carries. A device still trusting the old
key therefore cannot install a bundle signed with the new key; it rejects it outright. So a
new-signed bundle cannot simply be shipped to a fleet still on the old key.

Rotation instead moves the keyring in two bundles, in a fixed order:

- The **transition** bundle carries the NEW keyring baked into its rootfs, but is SIGNED WITH
  THE OLD key — so a device still trusting the old key accepts it. Once it installs and boots,
  that slot's `/etc/rauc/keyring.pem` is the new cert, and the device now trusts the new key.
- The **end-state** bundle carries the same NEW keyring and is SIGNED WITH THE NEW key.
  Installed to the other slot once the device trusts the new key, it brings BOTH slots onto the
  new key.

Get the order backwards — ship a new-signed bundle to a device that still trusts the old key —
and RAUC simply refuses to install it. It cannot brick the device; it will not install, full
stop.

## Safety model

Each phase installs to the **inactive** slot and reboots into it, the same A/B mechanism as an
ordinary OTA. `rauc-mark-good.service` marks a slot good only after a successful multi-user
boot; U-Boot auto-rolls-back a slot that fails to boot three times. The other slot always stays
bootable and trusting a key it can verify, so a failed rotation self-recovers — there is never a
window in which the device cannot verify an update.

`tools/rauc-rotate.sh` enforces this itself: after each reboot it requires the booted slot to
have **switched** away from the pre-phase slot, and its keyring fingerprint to equal the new
cert. If either check fails, it aborts with recovery guidance and does not proceed to the second
slot.

## The procedure

1. Generate the new key (never overwrites an existing one — a fresh rotation always gets a new
   named key):

   ```sh
   just rotate-keygen [name]
   ```

   Name the new key explicitly. `name` defaults to the key the fleet already trusts, which is
   never what a rotation wants, and both recipes refuse it rather than doing something plausible:
   `rotate-keygen` will not overwrite an existing pair, and `rotate-build` will not rotate a key
   to itself. Pick a fresh name — the year is the convention, e.g. `kiosk-2027`.

2. Build the two bundles:

   ```sh
   just rotate-build [name]
   ```

   Produces `build/rotation/transition.raucb` (old-signed) and
   `build/rotation/new-signed.raucb` (new-signed). Self-verifies that the keyring baked into the
   rootfs equals the new cert, via `debugfs`, before either bundle is treated as usable.

3. Provision SSH once per board, if key auth is not already set up (boards otherwise rely on
   debug-tweaks' empty-root-password):

   ```sh
   just rotate-provision-ssh root@<host>
   ```

4. Prove it on the HITL board first (`just find <cidr>` learns a board's address; see
   [`../README.md`](../README.md) on `kiosk-host`):

   ```sh
   just rotate-run root@<hitl-board> [name]
   just rotate-verify root@<hitl-board> [name] --empirical build/rotation/transition.raucb build/rotation/new-signed.raucb
   ```

   `--empirical` proves an OLD-signed bundle is now REJECTED and a NEW-signed one ACCEPTED — the
   falsifiable proof the rotation took, not just that a fingerprint matches.

5. Only then the prod board:

   ```sh
   just rotate-run root@<prod-board> [name]
   ```

   Prod is rotated over SSH by the exact process just proven on HITL — dogfooded, not flashed.
   Flashing a fresh card with the new keyring baked in is the fallback path, and must never
   precede the HITL proof.

## Verification

`just rotate-verify` compares the device's `/etc/rauc/keyring.pem` fingerprint to the new cert.
That check is cheap and deductive: the keyring is a single self-signed cert, so "keyring == new
cert" already means old-signed bundles are rejected — there is no other cert left for one to
verify against. `--empirical` goes further and feeds real bundles through `rauc info` on the
device, proving the same claim by exercising the actual signature check rather than reasoning
about it. That costs two ~114MB transfers, which is why it is opt-in and meant for the HITL
board rather than every prod rotation.

## Rotating to a new key: what to change by hand

Once a rotation has actually landed on every board, two places still name the old key, and
nothing updates them automatically. Until both are changed, `just flash` refuses every correct
card — it compares against the key named here, so a stale name turns a working image into a
rejected one and points the operator at the wrong file.

| Site | What to change |
|---|---|
| `Justfile` — `fleet-key` | The key name. Single source for the `flash` keyring guard and the rotation recipes' old-key default. |
| `kiosk-zero-w.yaml` — `AUTONOMOS_RAUC_KEY_DIR` | The same name. Separate because bitbake cannot read a `just` variable. |

Change them together, after the fleet is on the new key and verified — not before, or the build
starts signing with a key the devices do not yet trust.

## Retiring the old key

Once both boards are rotated and verified, the development key is retired: no device trusts it
any longer, so a bundle signed with it can no longer be installed anywhere in this fleet.

Purging `development.key.pem` from git history is a separate, largely cosmetic step — the key is
already public, so rewriting history does not undo the exposure. Rotation is what actually
removes it. `.gitleaks.toml` still allowlists the dev key's path; that entry can be removed once
the file itself is gone from the tree, not before.

The ordinary build signs with, and bakes the keyring of, this key: `kiosk-zero-w.yaml` sets
`AUTONOMOS_RAUC_KEY_DIR` to `local/keys/kiosk-2026`, which is gitignored, so a signing key cannot be
committed by accident the way this one was. Those four `AUTONOMOS_RAUC_*` variables are read by both
`update-bundle.bb` (which signs the bundle) and `rauc-conf.bbappend` (which bakes
`/etc/rauc/keyring.pem`), so the signer and the trusted keyring cannot drift apart.

## Files

- `tools/rauc-keygen.sh` — generates the new key and self-signed cert; refuses to overwrite.
- `tools/rauc-rotate-build.sh` — builds the transition and end-state bundles; verifies the baked
  keyring via `debugfs`.
- `tools/rauc-rotate.sh` — drives both phases on one device over SSH; enforces the
  slot-switched-and-fingerprint gate.
- `tools/rauc-rotate-verify.sh` — checks a device's trusted keyring, deductively or, with
  `--empirical`, by bundle.
- `tools/rauc-provision-ssh.sh` — installs this host's SSH public key on a device, once.
- `justfiles/rotate.just` — the `just` recipes wrapping all of the above.

`build/rotation/keydir` is not a key home. It is a copy `rauc-rotate-build.sh` makes for the
duration of a rotation build, so the transition bundle can be signed with the OLD key while
baking the NEW keyring — a pairing the ordinary build has no reason to express. The one key home
is `local/keys/<name>/`.
