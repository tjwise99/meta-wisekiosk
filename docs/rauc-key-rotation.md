# RAUC key rotation

Rotating the RAUC signing key the wisekiosk fleet trusts, and the ordering that rotation forces. See
[`layers-and-kas.md`](layers-and-kas.md) for how the bundle recipe and keyring fit into the build.

## Why rotate

A device verifies every update bundle's signature against `/etc/rauc/keyring.pem`. Upstream's keyring
is the public development certificate `development.cert.pem`, CN `AutonomOS Development Key`, whose
private key `development.key.pem` is committed beside it in the public `meta-autonomos-core` tree:
any clone of that repo can sign a bundle this kiosk accepts as authentic. This is issue **#6**, closed
by the rotation below.

Rotation replaces that keyring with a per-project key, CN `WiseKiosk Signing Key 2026`, generated by
`tools/rauc-keygen.sh` into `local/keys/<name>/` — **gitignored, so unlike the dev key it is never
committed or pushed, and no clone of this repo contains it.** It **lives in the working tree** only
because `kas-container` mounts the repository root and the build must read the key to sign with it;
a key held anywhere else is invisible. **Not committing it is the whole protection**, not where it
sits. The cost is that git cannot give it back — `git clean -xfd` deletes an untracked file and no
checkout restores it — so keep a **backup**, encrypted archive or password manager, for that alone.
Losing every copy ends OTA for every fielded unit: a device accepts only bundles signed by the key its
running slot trusts, leaving an SD card reflash as the only way back.

## Build prerequisite: the signing key must be present

`kiosk-zero-w.yaml` points `AUTONOMOS_RAUC_KEY_DIR` at `local/keys/kiosk-2026`, so **every** ordinary
build signs with that key and bakes its certificate as the device keyring. The key is never committed,
so a fresh clone arrives without one and halts `just build` during recipe parsing, before any task:

    ERROR: .../rauc-conf.bb: Unable to get checksum for rauc-conf SRC_URI entry
    signing.cert.pem: file could not be found

Intended: a missing key stops the build outright rather than falling back to another key and producing
an image the fleet rejects. Before the first build, restore
`local/keys/kiosk-2026/{signing.key.pem,signing.cert.pem}` from the backup — or, for a new fleet, `just
rotate-keygen kiosk-2026`. Restoring is the normal case: a device trusts only the certificate baked into
its running slot, so a *fresh* key buys no access to a fielded fleet — that takes a full rotation,
below, and `rauc-keygen.sh` refuses to overwrite an existing pair for the same reason. Reflashing the
card is the only way to un-rotate a fielded unit: RAUC never rewrites the boot partition, so no OTA
repairs a card written with the wrong keyring. `just flash` therefore verifies the image's baked
`/etc/rauc/keyring.pem` against this key, refusing to write if they differ or if the image and rootfs
artifacts come from different builds.

## The ordering constraint

A device verifies a bundle's signature against the keyring in the slot it is **currently running
from**, not against whatever the new bundle carries, so a device on the old key rejects a new-signed
bundle outright — RAUC refuses to install it, so the wrong order cannot brick a device. Rotation
moves the keyring in two bundles, in a fixed order:

- The **transition** bundle carries the NEW keyring baked into its rootfs but is SIGNED WITH THE OLD
  key, so a device on the old key accepts it. Installing and booting it makes that slot's
  `/etc/rauc/keyring.pem` the new cert.
- The **end-state** bundle carries the same NEW keyring and is SIGNED WITH THE NEW key. Installed to
  the other slot from a device that trusts the new key, it brings BOTH slots onto it.

## Safety model

Each phase installs to the **inactive** slot and reboots into it, the same A/B mechanism as an
ordinary OTA. `rauc-mark-good.service` marks a slot good only after a successful multi-user boot;
U-Boot auto-rolls-back a slot that fails to boot three times. The other slot stays bootable and
trusting a key it can verify, so a failed rotation self-recovers — there is no window in which the
device cannot verify an update. `tools/rauc-rotate.sh` enforces this itself: after each reboot the
booted slot must have **switched** away from the pre-phase slot, and its keyring fingerprint must
equal the new cert. Either check failing aborts with recovery guidance, short of the second slot.

## The procedure

1. **Generate the new key** — `just rotate-keygen [name]`. Name it explicitly: `name` defaults to the
   key the fleet already trusts, which a rotation never wants. Both recipes refuse that rather than
   doing something plausible — `rotate-keygen` will not overwrite an existing pair, `rotate-build`
   will not rotate a key to itself. Convention is the year, e.g. `kiosk-2027`; the CN drops the
   prefix, minting `WiseKiosk Signing Key 2027`.

2. **Build the two bundles** — `just rotate-build [name]` — `transition.raucb` (old-signed) and
   `new-signed.raucb` (new-signed), under `build/rotation/`. The build self-verifies via `debugfs`
   that the keyring baked into the rootfs equals the new cert before either is treated as usable.

3. **Provision SSH** — `just rotate-provision-ssh root@<host>` — once per board, where key auth is
   not set up; boards otherwise rely on debug-tweaks' empty-root-password.

4. **Prove it on the HITL board first** (`just find <cidr>` learns a board's address; see
   [`../README.md`](../README.md) on `kiosk-host`). `--empirical` proves an OLD-signed bundle is
   REJECTED and a NEW-signed one ACCEPTED — falsifiable proof the rotation took, not just a
   fingerprint match.

       just rotate-run root@<hitl-board> [name]
       just rotate-verify root@<hitl-board> [name] --empirical build/rotation/transition.raucb build/rotation/new-signed.raucb

5. **Only then the prod board** — `just rotate-run root@<prod-board> [name]` — over SSH by the exact
   process just proven on HITL, dogfooded not flashed. Flashing a fresh card with the new keyring
   baked in is the fallback path, and must never precede the HITL proof.

## Verification

`just rotate-verify` compares the device's `/etc/rauc/keyring.pem` fingerprint to the new cert — cheap
and deductive, since the keyring is a single self-signed cert, so "keyring == new cert" already means
old-signed bundles are rejected: no other cert is left for one to verify against. `--empirical` proves
the same claim by exercising the real signature check, feeding bundles through `rauc info` on the
device. It costs two ~114MB transfers, hence opt-in and meant for the HITL board.

## Rotating to a new key: what to change by hand

Two sites name the key by hand and nothing updates them. While either is stale, `just flash` rejects
every correct card: it compares against the name given there, so a stale name fails a good image and
points the operator at the wrong file. Change them together, after the fleet is on the new key and
verified — earlier, and the build signs with a key the devices do not trust.

| Site | What to change |
|---|---|
| `Justfile` — `fleet-key` | The key name. Single source for the `flash` keyring guard and the rotation recipes' old-key default. |
| `kiosk-zero-w.yaml` — `AUTONOMOS_RAUC_KEY_DIR` | The same name. Separate because bitbake cannot read a `just` variable. |

## Retiring the old key

With both boards rotated and verified, no device trusts the development key, so a bundle signed with
it installs nowhere in this fleet. Purging `development.key.pem` from git history is a separate,
largely cosmetic step: the key is public, so rewriting history does not undo the exposure. Rotation is
what removes its reach. `.gitleaks.toml` allowlists the path the **vendored** copy had, because
`gitleaks detect` scans git history, where the blob still is, at `c2d73ed3` (2026-01-04); the worktree
copy left with the vendored tree, and the kas-fetched one sits under gitignored `sources/`, never
scanned. That entry goes only if the history is rewritten — not when the file leaves the tree, which
it already has.

`kiosk-zero-w.yaml` sets `AUTONOMOS_RAUC_KEY_DIR` to the gitignored `local/keys/kiosk-2026`, so a
signing key cannot be committed by accident the way this one was. Both `update-bundle.bb` (signs the
bundle) and `meta-autonomos-core`'s `rauc-conf.bbappend` (bakes `/etc/rauc/keyring.pem`) read the same
`AUTONOMOS_RAUC_*` variables, so signer and trusted keyring cannot drift apart.

## Files

- `tools/rauc-keygen.sh` — new key and self-signed cert; refuses to overwrite.
- `tools/rauc-rotate-build.sh` — the two bundles; `debugfs`-verifies the baked keyring.
- `tools/rauc-rotate.sh` — drives both phases on one device over SSH; enforces the slot-switched gate.
- `tools/rauc-rotate-verify.sh` — checks a device's trusted keyring, deductively or by bundle.
- `tools/rauc-provision-ssh.sh` — installs this host's SSH public key on a device, once.
- `justfiles/rotate.just` — the `just` recipes wrapping all of the above.

`build/rotation/keydir` is scratch: `rauc-rotate-build.sh` copies both keys there so the rotation
build can sign the transition bundle with the OLD key while baking the NEW keyring, a pairing the
ordinary build has no reason to express. It stages private keys, so the directory is `700` and each
key `600`, matching `local/keys/<name>/` — a copy, not a key home; the key lives there, and
`git clean -xfd` discards both.
